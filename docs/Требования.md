# Требования

Все R1–R12 обязательны для любой темы. Точные поля и ошибки заданы в [контракте](<Данные и API.md>), проверка — в [приёмке](Приёмка.md).

## R1. Задача и собственное содержание

В коротком ТЗ: аудитория, цель, сценарии «найти / забронировать / отменить», ограничения, три категории, подпись `feature` и **два проверяемых критерия удобства** для своей темы. Зафиксируйте исходные требования до основной реализации; изменения сопровождайте причиной.

Подготовьте **не менее 12 предложений в трёх категориях, минимум по три в каждой**: собственные названия, содержательные описания и характеристики. `feature` видна в карточке/подробностях и помогает выбирать. Название сервиса, палитра, типографика, сетка, интервалы, карточки и тексты состояний образуют целостное оформление. Оценивается удобство и обоснованность решений.

Данные вымышленные, учебный характер обозначен, источники заимствований указаны. Работайте через понятные изменения Git и PR; минимального числа коммитов нет.

## R2. Вёрстка и доступность

Заголовок и описание сервиса, каталог, подробности, форма, список заявок; достаточно одной страницы. Семантический HTML, иерархия заголовков, **Grid и Flexbox**, БЭМ, CSS-переменные цветов/интервалов; оформление не дублируется в JS-обработчиках.

На **360 и 1280 px** нет горизонтальной прокрутки страницы, наложений и недоступных элементов. Основные действия работают с Tab, Enter/Space; виден фокус, есть подписи полей, alt изображений и доступные сообщения об ошибках/отправке. Одно уместное CSS-состояние/анимация учитывает `prefers-reduced-motion`. Изображение или собственный SVG подключены как ресурс сборки и работают после build.

## R3. Каталог и выбор

Каталог приходит из API. Поиск по названию (trim, без учёта регистра) и категория работают совместно; видны счётчик и пустой результат со сбросом. Фильтровать можно на клиенте.

Выбрано максимум одно предложение: оно показано в подробностях и форме. Скрытие карточки фильтром сохраняет выбор и ввод. Сброс фильтров не очищает форму или серверные данные. Различаются загрузка, данные, пустой ответ и ошибка с повтором; перезагрузка не создаёт дубликатов, отказ не стирает уже известные данные без объяснения.

## R4. Форма и браузерные хранилища

Используйте `form`, `submit`, `FormData` и runtime-проверку полей по контракту. Enter и кнопка запускают один сценарий. При отказе сохраняйте ввод и объясняйте причину; на время POST исключайте повтор и в обработчике, и в интерфейсе. Успех — после сохранения: поля очищаются, количество становится 1, выбор остаётся, черновик удаляется.

- **localStorage:** явное сохранение черновика и восстановление после перезагрузки. «Очистить форму» удаляет поля, выбор и черновик, сохраняя серверные заявки. Если предложение исчезло, предупредите и сохраните остальные поля без отправки.
- **sessionStorage:** поиск и категория восстанавливаются в той же вкладке. Объясните отличие времени жизни от localStorage.
- Повреждённый JSON или недоступное хранилище дают понятное сообщение, не блокируют работу и не удаляют чужие ключи. Восстановленный черновик не резервирует ресурс: актуальный остаток проверяет сервер.

## R5. Бронирование и отмена

Заявка занимает **1–5 единиц** одного предложения. Остаток = ёмкость − сумма количества его **активных** заявок. Точный остаток разрешён; превышение отклоняется без изменения данных.

В списке видны количество и статус, новые заявки первыми. Отмена переводит заявку в `cancelled`, освобождает ресурс один раз и сохраняет запись в истории. Создание/отмена обновляют список, каталог и подробности по ответам сервера.

Если POST успешен, а следующий GET нет, сообщите о сохранённой заявке и предложите обновить данные; автоматически повторять POST нельзя. Все заявки общие, аккаунтов нет.

## R6. TypeScript и модули

Frontend — TypeScript с `strict`: модель предложения/заявки/статусов, типизированные границы функций, проверка неизвестных данных FormData, storage и HTTP. `as`, `any` и подавления диагностики не заменяют проверку.

Разделите UI, API, проверку ввода/расчёты и браузерное хранение. Расчёт остатка — чистая функция без мутации входа, DOM и файлов; правило не копируется по обработчикам. Общее ядро клиента/сервера допустимо, независимая серверная проверка обязательна. Осмысленно примените готовый generic и объясните параметр типа; собственного сложного обобщения не требуется.

## R7. Web Components

Минимум один повторно используемый **Custom Element** с документированным публичным входом данных и собственным событием выбора с id. Контроллер не ищет внутренние кнопки компонента. Используйте **Shadow DOM** и lifecycle для подключения/очистки обработчиков. Обновление данных, переподключение и клавиатура работают без двойных событий и накопления обработчиков.

## R8. Node.js и файлы

Собственный сервер на Node.js с **HTTP и File System**, JS или TS, по общему контракту. Без Express/NestJS, БД и ORM. Сервер независимо проверяет запрос, назначает id/время/статус, рассчитывает остаток и подтверждает успех после записи. Ошибки не создают ложный успех или необработанное завершение процесса.

Seed хранится в `data/`, изменяемые JSON-файлы — отдельно и вне Git. Достаточно одного процесса и последовательных запросов; эту границу укажите в README. Инициализация, сброс и обработка повреждённых файлов описаны в контракте.

## R9. Команды и инструменты

| Команда | Требуемый результат |
| --- | --- |
| `npm ci` | Установка по согласованному lockfile |
| `npm run dev` | Запуск разработки; команды обоих терминалов, если нужны, описаны |
| `npm run typecheck` | Проверка frontend и общего TS-кода без выпуска файлов |
| `npm run lint` | ESLint и Stylelint проверяют исходники |
| `npm run format:check` | Prettier проверяет без записи |
| `npm test` | Однократный Vitest с кодом возврата |
| `npm run build` | Проверка типов → Vite; ошибка останавливает выпуск новой сборки |
| `npm run preview` | Свежая сборка frontend с работающим доступом к API |
| `npm run check` | Типы → линтеры → форматирование → тесты → сборка; любой отказ останавливает цепочку |
| `npm start` | Сервер готового приложения |
| `npm run seed` | Явный сброс учебных данных при остановленном сервере |

В основе `build` пока вызывает только Vite; `start`/`seed` и тесты предстоит добавить. `check:starter` не заменяет итоговый `check`. Согласуйте `.nvmrc`, `engines`, lockfile, Docker/CI и README. Различайте исходники, dev, dist и preview: старый dist не подтверждает успешную сборку.

При изменении структуры адаптируйте области проверок: текущий typecheck охватывает `src/` и `tests/`, ESLint — JS/TS, Stylelint — отдельные CSS-файлы, Prettier — код/HTML/JSON/YAML. CSS внутри строк Shadow DOM проверяйте вручную или настройте его извлечение. Сервер на TS требует настройки типов и запуска. Собственные исходники нельзя исключать ради успешной проверки.

## R10. Контейнер, CI и публикация

Dockerfile и Compose запускают всё приложение; допустим один Node.js-контейнер, отдающий `dist` и `/api`. Рабочие данные в **volume** переживают пересоздание контейнера. В README: запуск `docker compose up --build`, остановка, порт, переменные, каталог данных, первичная инициализация, отдельный сброс и логи. Нужны `.dockerignore`, воспроизводимая сборка и отсутствие секретов в образе.

GitHub Actions запускает `npm ci` и `check` на PR и основной ветке. После успешной проверки основной ветки — публикация образа в registry с тегом/идентификатором версии. Подтвердите pull/run опубликованного образа; для PR достаточно проверок.

Через Actions опубликуйте на **GitHub Pages страницу проекта**: описание, два собственных скриншота, репозиторий, выпуск и инструкция запуска. Pages показывает страницу проекта; полный сервис с Node.js проверяется в контейнере. Платный сервер не нужен. Если registry/Pages недоступны, преподаватель назначает эквивалент: CI-артефакт образа с import/run и площадку статической публикации.

## R11. Проверки

Выполните [S01–S18 и U1–U4](Приёмка.md). В отчёте: версия/среда, условия, фактический результат, статус и свидетельство. Для двух найденных дефектов — воспроизведение, причина, исправление, повторная и соседняя проверка. Если дефектов не было, исследуйте два риска и запишите проверки гипотез без выдуманных исправлений.

Unit-тесты импортируют вашу реализацию; mock подменяет транспорт, а не расчёт. Подтвердите падение теста при временной ошибке правила и восстановите код. Процент покрытия и число тестов не заданы. У существенного элемента UI должен быть стабильный `data-testid`; E2E не обязательны.

## R12. Самостоятельность и помощь ИИ

ИИ допустим как консультант: объяснить понятие или диагностику, разобрать ваш фрагмент, дать локальную подсказку, предложить случай для проверки. Изменения и проверку выполняете сами.

Нельзя поручать ИИ реализацию требований, готовые модули, тесты, конфигурации, контент каталога, ТЗ, отчёт или описание PR — целиком либо последовательностью мелких запросов. Это относится и к агентам в редакторе, и к генеративному автодополнению. Понимание полученного готового решения не заменяет самостоятельное выполнение. Выданную основу и официальные примеры можно использовать с указанием источника и собственной адаптацией.

В итоговом PR кратко укажите инструмент, задачу консультации и что сделали/проверили сами; если ИИ не использовали, так и напишите. Отдельный журнал диалогов не нужен. Источники и помощь не скрывайте, проверки не выдумывайте.

На [защите](<Оценивание и защита.md>) объясните выбранные преподавателем части и самостоятельно внесите небольшую правку без ИИ. Правила для помощников находятся в [AGENTS.md](../AGENTS.md); их удаление не меняет условий задания.

## Границы проекта

Не требуются авторизация, платежи, реальные персональные данные, динамический календарь, доставка, сложные роли, редактор каталога, React/Angular, микросервисы и промышленная конкурентность. Бонусные ловушки ДЗ 1-7 необязательны. Расширения согласуйте с преподавателем: они не заменяют R1–R12 и не увеличивают максимум оценки.
