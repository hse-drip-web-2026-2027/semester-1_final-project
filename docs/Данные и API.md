# Общие данные и HTTP-контракт

Контракт одинаков для 30 тем. Технические имена не меняются; пользовательские названия и единица бронирования зависят от темы. Предложения — фиксированный учебный каталог, заявки — изменяемые данные.

## 1. Модель

### Предложение — Item

| Поле | Правило |
| --- | --- |
| `id` | Непустой уникальный строковый идентификатор, стабильный между запусками |
| `title` | Содержательное название, 3–80 символов после trim |
| `category` | Один из трёх идентификаторов категорий вашего ТЗ |
| `description` | Описание 40–400 символов; что именно получает пользователь |
| `feature` | Значение тематической характеристики, 1–80 символов; подпись характеристики одна на проект и указана в ТЗ |
| `capacity` | Целое число от 3 до 20; общее количество единиц предложения |
| `remaining` | Только в ответе API: capacity минус сумма quantity активных заявок этого id |

Изображения, категории и подпись feature можно задать в конфигурации frontend. В стартовом каталоге не менее 12 объектов; предложения с техническими id **`item-a` и `item-b` имеют capacity 5 и 8**. Их названия и описания относятся к выбранной теме. Начальные заявки отсутствуют.

### Заявка — Booking

| Поле | Правило |
| --- | --- |
| `id` | Уникальная строка, назначается сервером |
| `itemId` | id существующего предложения |
| `name` | Строка после trim, 2–60 символов |
| `email` | Строка после trim, до 120 символов, без пробелов, учебный формат `часть@часть.часть` |
| `quantity` | Число, целое от 1 до 5; JSON-строка `"2"` в API не принимается |
| `comment` | Необязательная строка, до 200 символов; при отсутствии хранится `""`; сохраняется как обычный текст без исполнения разметки |
| `status` | Только `active` или `cancelled`; при создании сервер ставит active |
| `createdAt` | ISO-строка времени создания, назначается сервером; при отмене не меняется |

Клиент преобразует FormData в данные контракта: строку количества очищает по краям и проверяет до преобразования. Пустая строка не равна нулю. Исходные name/email нормализуются trim на сервере; comment сохраняется без изменения символов. Используйте один согласованный учебный алгоритм email в форме и на сервере, без проверки существования адреса.

Сервер независимо проверяет поля, itemId и остаток. Поля вне списка соответствующего маршрута отклоняются с 400. Отказ не создаёт запись и не меняет остаток.

## 2. Маршруты

JSON в UTF-8. Успешные ответы — массив/объект напрямую, без обёртки `{data: ...}`.

| Метод и путь | Запрос | Успех |
| --- | --- | --- |
| `GET /api/items` | Без тела | 200, массив предложений с актуальным remaining |
| `GET /api/items/:id` | Без тела | 200, одно предложение с remaining |
| `GET /api/bookings` | Без тела | 200, массив заявок: новые первыми; при одинаковом времени порядок стабилен |
| `POST /api/bookings` | itemId, name, email, quantity, необязательный comment | 201, созданная заявка целиком; только после записи файла |
| `PATCH /api/bookings/:id` | Только `{"status":"cancelled"}` | 200, отменённая заявка целиком; повторная отмена возвращает ту же запись без повторного освобождения |

Порядок при равных createdAt определите в README. DELETE и изменение количества заявки не требуются.

## 3. Ошибки

Форма: `{"error":{"code":"...","message":"понятная причина"}}`. Сообщения могут различаться по теме; code и условия едины.

| Статус | code | Условие |
| --- | --- | --- |
| 400 | `INVALID_JSON` | Тело POST/PATCH не разбирается как JSON |
| 400 | `VALIDATION_ERROR` | Не объект, отсутствует поле, неверны тип/граница/статус, есть неизвестное поле |
| 404 | `NOT_FOUND` | Неизвестный маршрут, id предложения или заявки |
| 405 | `METHOD_NOT_ALLOWED` | Путь известен, но метод не поддержан; указать Allow |
| 409 | `CAPACITY_EXCEEDED` | quantity допустимо само по себе, но больше актуального остатка |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | Для POST/PATCH отсутствует application/json; параметр charset допустим |
| 500 | `STORAGE_ERROR` | Ошибка чтения/записи рабочих данных; успех не показывается |

Для одного запроса проверяйте: маршрут/метод → Content-Type → JSON → поля → существование связанного объекта → остаток → запись. При проверке 400 держите прочие условия корректными. `fetch` может успешно вернуть Response при HTTP-ошибке: клиент проверяет `response.ok`, а также отдельно обрабатывает отказ сети.

Отказ записи проверяйте на копии данных или подменённом хранилище. При неопределённом сетевом исходе клиент предлагает обновить список перед повтором; автоматического повторного POST нет.

## 4. Файловое хранение

Каталог и заявки хранятся в одном или двух JSON-файлах через File System. `remaining` вычисляется, а не хранится независимым счётчиком.

При первом запуске с **отсутствующим** рабочим файлом создайте его из seed. Существующий файл не перезаписывается при старте. Повреждённый существующий файл — ошибка, а не повод молча удалить заявки и восстановить seed. При неудачной записи состояние в памяти также не должно считаться успешно изменённым.

`npm run seed` явно возвращает учебный каталог и пустой список заявок; перед ним сервер остановлен и не выполняет операции. Путь задаётся конфигурацией и документируется; в контейнере это смонтированный volume. Поддерживаемый режим: один процесс, последовательные запросы.

В README обоснуйте JSON и приведите заголовок и две строки плоского CSV-экспорта каталога с экранированием запятой/кавычки. CSV-endpoint не нужен.

## 5. Доверие и границы

Пользовательский ввод, включая `<b>пример</b>`, отображается как текст, без innerHTML. Статический шаблон компонента допустим. Данные HTTP/storage проверяются во время выполнения.

Mock допустим для разработки и диагностики с явным обозначением. Итоговый сценарий использует реальный HTTP и сохраняет заявки после перезапуска сервера.
